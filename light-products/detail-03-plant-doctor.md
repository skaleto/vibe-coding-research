## A. 完整 Prompt v1

### A.1 诊断 Prompt 完整字符串（system + user 模板 + JSON schema）

#### A.1.1 System Prompt（约 920 字）

```text
你是一名以资深植物病理学家 + 园艺师口吻提供参考建议的 AI 助手，专长于家庭室内观叶植物（多肉、龟背竹、绿萝、文竹、君子兰）、阳台果蔬（番茄、辣椒、草莓）、常见花卉（月季、兰花、仙人掌科）的病害诊断与日常养护。你必须明确标注“AI 诊断仅供参考”，不能伪装成真人专家，也不能替代本地园艺师或农资人员。

# 核心原则

1. **诊断三段法**：观察症状 → 假设病因（按可能性列 3 个）→ 给可执行处理方案。绝不只说"可能是浇水问题"这种空话。
2. **以救活为目标**：用户最关心的是"还能不能救"。一定要给恢复可能性（高/中/低）+ 观察周期 + 失败兜底（如"若 14 天后未见好转，建议剪枝重新扦插")，不要给精确恢复可能性。
3. **可执行性**：每一步处理方案必须告诉用户"今天/明天具体做什么"，不要给"加强通风"这种抽象建议；要给"把花盆移到窗台距离窗框 30cm 内的位置，每天开窗 2 小时"这种动作指令。
4. **谨慎不夸大**：恢复可能性为“低”时必须诚实说明并建议剪枝/扦插/换新；图片不清时主动要求补图，不要硬猜。
5. **30 天日历**：每次诊断都必须输出未来 30 天的护理日历（按"天 → 动作"格式），覆盖浇水/施肥/咨询处理/光照/通风/换盆 6 类动作。

# 严格禁止

- ❌ 不要推荐具体农药商品名、通用农药名或剂量比例；如怀疑病虫害严重，只能提示咨询本地花卉店/园艺师/农资人员并严格阅读产品说明
- ❌ 不要建议剂量或稀释比例（包括"按产品说明处理"这类表达）；如确需用药，只能建议用户咨询本地花卉店/园艺师/农资人员并严格阅读产品说明
- ❌ 不要诊断动物、宠物、人体疾病
- ❌ 不要推荐"中草药治病"或任何医疗用途的植物使用
- ❌ 不要在没有图像的情况下给出确定性诊断，无图时必须降级为"建议补图"

# 输入字段

用户每次诊断会提供：
- `image_url_array`: 1-3 张图片 URL（顺序：叶子特写 → 全株 → 环境/盆土）
- `water_freq`: 用户描述的浇水频率（如"每周 2 次"/"凭手感不干透不浇"/"不记得了"）
- `light`: 光照条件（"全日照 / 散射光 / 室内补光灯 / 阴暗角落 / 不确定"）
- `soil`: 土壤情况（"普通营养土 / 多肉颗粒土 / 自配土 / 不知道"）
- `description`: 用户文字补充症状（可选，可为空）
- `plant_self_report`: 用户认为的植物名（可选，用户可能猜错，以你的判断为准）

# 输出格式（严格 JSON，禁止 Markdown 包裹）

完全按以下 schema 输出，所有字段都必填，不输出任何 JSON 之外的文字：

{
  "plant_name": "中文俗名（如'锦晃星'）",
  "scientific_name": "拉丁学名（如 Echeveria pulvinata）",
  "confidence": "0.0-1.0 的识别置信度",
  "image_quality_ok": true | false,
  "image_quality_feedback": "图片不清晰时的具体建议（如'请补拍叶背特写'），清晰时填空字符串",
  "diagnosis": [
    {
      "cause": "病因短描述（如'根腐病初期'）",
      "likelihood": "高",
      "evidence": "你从图片看到的证据（如'下层叶片发黄+茎基部黑褐色'）",
      "severity": "轻 | 中 | 重"
    }
  ],
  "action_steps": [
    "第 1 步：今天立刻断水，把花盆从托盘中取出晾干",
    "第 2 步：明天清晨用消毒剪刀剪去发黑的叶片和烂根",
    "..."
  ],
  "prognosis": {
    "recovery_outlook": "高",
    "time_to_observe": "2-3 周",
    "fallback_if_fail": "若 14 天后茎基部仍黑褐色，建议剪取健康顶芽扦插"
  },
  "calendar_30d": [
    {"day": 1, "action": "断水 + 移至通风处", "type": "watering"},
    {"day": 3, "action": "继续观察腐烂是否扩散；如恶化，带照片咨询花卉店或园艺师", "type": "observation"},
    {"day": 7, "action": "观察叶片是否继续软化", "type": "observation"}
  ],
  "disclaimer": "本诊断由 AI 基于图像生成，仅供参考。严重病害建议咨询当地花卉市场或园艺师。"

# 边界场景

- 若图片中没有植物（用户拍了天空/地板/人脸）→ image_quality_ok=false，且 diagnosis 数组为空，仅在 image_quality_feedback 中说明
- 若用户上传的是宠物/动物 → 拒绝诊断并提示"本工具只服务于植物"
- 若识别为大麻、罂粟等违禁植物 → plant_name 填"无法识别"，diagnosis 为空，feedback 提示"建议咨询专业人士"
- 若是健康植物（image_quality_ok=true 但找不到病害）→ diagnosis 数组里写一个 cause="未见明显病害"，likelihood="高"，calendar_30d 给常规养护日历
```

### A.3 病虫害合规处理规则

**绝对原则**：AI 不输出具体农药商品名、通用药剂名、剂量、稀释比例或替代性偏方。严重病虫害只提示用户带照片咨询本地花卉店、园艺师或农资人员，并遵循当地法规与产品标签。

**允许输出**：
- 非药物养护动作：隔离、剪除病叶、销毁病果、改善通风、调整光照、控水、换土、清洁工具
- 安全提醒：食用类植物处理后采摘需遵循专业人员或产品标签要求；家中有孕妇、婴幼儿、宠物时要避免接触
- 咨询建议：症状扩散、食用作物病害、虫害爆发时咨询本地专业人员

**禁止输出**：
- 任何商品名、品牌名、农药通用名或处方式替代名
- 任何剂量、稀释比例、喷洒频次、混配方案
- 任何高毒、禁限用药剂或未经验证的民间偏方

**风险免责声明**（每次涉及严重病虫害时必须附加）：

```
⚠️ 安全提醒
本诊断由 AI 基于图像生成，仅供家庭园艺参考。
若病虫害扩散、涉及食用植物、或家中有孕妇/婴幼儿/宠物，请带照片咨询本地花卉店、园艺师或农资人员，并遵循当地法规与产品标签。
```

**Prompt 内嵌规则**（system prompt 已包含）：
```
当 action_steps 需要涉及病虫害控制时：
1. 优先给隔离、修剪、通风、控水、清洁等非药物动作
2. 不输出药剂名、剂量、稀释比例、喷洒频次
3. 若症状严重，追加“请带照片咨询本地花卉店/园艺师/农资人员”
```

## B. 病害知识库样本（25 个高频病害）

### B.2 25 个病害样本

#### 1. 多肉黑腐病
- **学名**：Pythium / Phytophthora spp.（疫霉菌）
- **症状**：① 茎基部黑褐色水浸状斑 ② 叶片由下至上发软透明 ③ 整株散发腐臭味 ④ 用手轻碰叶片脱落 ⑤ 切口黑色蔓延
- **病因**：① 浇水过多致积水（高/中/低）② 高温高湿不通风（高/中/低）③ 土壤带菌或换盆未消毒（高/中/低）
- **处理**：① 立即脱盆晾根 ② 切除所有黑色组织至健康部位 ③ 保持切口干燥，可少量撒草木灰 ④ 晾干 24-48 小时后重新上盆（颗粒土） ⑤ 7 天断水，第 8 天沿盆边少量给水
- **预防**：① 颗粒土比例 ≥70% ② 夏季高温少浇水或断水 ③ 通风条件差时不闷养
- **恢复可能性**：中（重症偏低）
- **见效时间**：2-4 周

#### 2. 绿萝叶黄
- **学名**：Epipremnum aureum 非生理性黄叶
- **症状**：① 叶片均匀发黄（缺光）或老叶先黄（缺水/缺氮）② 黄叶边缘焦枯（光强/水少）③ 黄叶柔软无光泽 ④ 黄叶根部还有新芽
- **病因**：① 光照不足或过强（高/中/低）② 浇水节奏失调（高/中/低）③ 长期未换盆缺养分（高/中/低）
- **处理**：① 移至明亮散射光处（距窗 1m 内） ② 检查土壤干湿，干透浇透 ③ 剪除大面积黄叶 ④ 每月 1 次稀薄复合肥水 ⑤ 1 年以上未换盆需换新土
- **预防**：① 远离空调/暖气直吹 ② 不要让花盆长期积水 ③ 每月转盆 1 次让受光均匀
- **恢复可能性**：高
- **见效时间**：2-3 周

#### 3. 番茄早疫病
- **学名**：Alternaria solani
- **症状**：① 下层老叶先出现褐色同心圆状斑 ② 病斑直径 0.5-2cm ③ 病斑周围有黄晕 ④ 严重时整株落叶 ⑤ 果实近果柄处也有褐色凹陷斑
- **病因**：① 高湿+昼夜温差大（高/中/低）② 田间通风不良（高/中/低）③ 种子带菌或连作（高/中/低）
- **处理**：① 立即剪除所有病叶并销毁（不堆肥） ② 病株与健康植株拉开距离 ③ 症状继续扩散时咨询本地园艺或农资人员 ④ 增加株间距、绑蔓打杈 ⑤ 雨季避免叶面浇水
- **预防**：① 苗期开始定期检查下层叶 ② 与非茄科作物轮作 ③ 浇水改为根部滴灌
- **恢复可能性**：中
- **见效时间**：1-2 周

## D. 图像 API 成本控制方案（命脉章节）

### D.1 三大 API 对比表

| 维度 | GPT-4o Vision | 智谱 GLM-4V-Plus | 通义万相 Qwen-VL-Max |
|---|---|---|---|
| **单次成本（200KB 图片）** | ¥0.06-0.10 | ¥0.02-0.05 | ¥0.015-0.03 |
| **病害诊断质量（自测）** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **中文植物名识别** | 良好（依赖 prompt） | **优秀**（中文原生） | 优秀 |
| **JSON 结构化输出稳定性** | **优秀** | 良好（偶尔漏字段） | 一般（需要 retry） |
| **响应速度** | 8-15 秒 | 5-10 秒 | 6-12 秒 |
| **API 稳定性** | 海外节点 99.9% | 国内 99.5% | 国内 99.7% |
| **国内接入便利** | 需走 OpenRouter/代理 | 直连 | 直连 |
| **超时率（自测）** | 2% | 5% | 8% |
| **每月免费额度** | 无 | 25 元 | 200 万 token |

**选型策略**：
- **主**：智谱 GLM-4V-Plus（中文好 + 国内直连 + 成本中等）
- **备**：通义万相 Qwen-VL-Max（成本最低，作为预算告急时的降级）
- **付费用户专享高质量**：GPT-4o Vision（仅年卡用户或主动选择"高精度诊断"时调用，按 +¥0.5 加价）

### D.2 缓存策略（关键省钱招）

**Layer 1：图片 hash 完全复用**
- 上传图片后服务端计算 SHA-256 + perceptual hash（pHash）
- 完全相同图片 → 直接返回历史结果（不调 API），用户感知"诊断超快"
- 命中率预估 5-10%（用户重新上传 / 朋友分享同一张图）

**Layer 2：相似图片软匹配（pHash 距离 < 5）**
- 同一用户在 3 分钟内重传相似图片（如换角度拍同一盆植物）
- 复用结果但标注"基于相似图片，结果仅供参考"
- 节省高频用户重复诊断成本，命中率预估 3-5%

**Layer 3：相同病害模板复用（语义缓存）**
- 服务端维护 200+ 病害模板（B 章节知识库）
- AI 诊断给出"病害类型 + 严重度"后，从模板库取通用的 calendar_30d 和 action_steps（仅个性化部分用 AI 生成）
- 节省约 70% token（仅生成识别 + 诊断部分，模板部分复用）
- 命中率预估 >=60%

**Layer 4：30 天日历的缓存**
- calendar_30d 大部分是模板化内容，按"病害类型 × 季节 × 城市气候"维度预生成
- 用户诊断时仅调 API 生成"病害诊断"小部分，日历部分从模板库拼装

**实施 ROI 估算**：
- 不缓存：1000 次诊断 = 1000 次 API 调用 × ¥0.05 = ¥50
- 全部三层缓存：1000 次诊断 = 300 次 API（节省约 70%）= ¥15
- **节省约 70%！每月省 ¥3500（按 10 万次诊断）**

### D.3 防刷策略

**多层 rate limit**：

| 维度 | 限制 | 触发动作 |
|---|---|---|
| 单 IP | 20 次/天 | 第 21 次起返回 429 + 验证码 |
| 单设备（IDFA/Android ID） | 5 次/天（免费用户）/ 100 次/天（付费） | 超过弹付费墙 |
| 单用户（登录） | 3 次/天（免费） / 50 次/天（包月） / 200 次/天（年卡） | 超过弹付费墙 |
| 单图片 hash | 24 小时内同 hash 仅算 1 次 | 自动从缓存返回 |
| **预算总量** | 每日 ¥200 总成本上限 | 触发 → 全局降级到 Qwen-VL-Max |

**异常行为识别**：
- 同一 IP + 同一图片 hash 在 5 分钟内重传超过 3 次 → 拉黑 1 小时
- 单设备一天调用超过 50 次 → 标记可疑
- API 返回 image_quality_ok=false 占比 > 60% 的用户 → 风控审核

**用户层面体验**：
- 普通触发限流 → 友好提示"今天的免费次数用完了，明天再来"
- 可疑行为 → 拉到付费墙引导付费
- 极端行为 → 拉黑 24 小时

### D.4 图片预处理（关键省 token）

**前端压缩管线**（在调用 API 前必须）：

```
原图（用户拍照通常 3-8MB，4032×3024）
  ↓ Step 1：客户端用 react-native-image-resizer
缩放到长边 1024px，质量 85%（约 400KB）
  ↓ Step 2：上传到 R2/OSS
服务端用 sharp / imagemagick
  ↓ Step 3：拼接（如有多张图）
3 张图竖直拼接成 1 张 1024×1800，质量 80%
  ↓ Step 4：JPEG 转 WebP
最终大小 < 200KB
  ↓ Step 5：base64 编码传给 LLM
```

**多图拼接策略**：
- 用户上传 3 张图 → 不分 3 次调 API，而是拼成 1 张大图
- LLM 一次看 3 张图能交叉验证（叶子特写+全株+环境），准确率反而更高
- 成本节省约 67%（1 次 API 替代 3 次）

**WebP 转换的省钱效果**：
- JPEG 80% 质量 200KB 的图 → WebP 同质量约 100-130KB
- LLM 按图片字节大小计费，**节省 30-40%**
- 仅 OpenAI 等部分 API 支持 WebP，智谱 / 通义需要保留 JPEG

- 各 LLM 成本占比

## 附录：技术细节

### 附 A：Cloudflare Workers 关键代码示例

```typescript
// POST /diagnose
export async function diagnose(request: Request, env: Env) {
  const { imageUrl, waterFreq, light, soil, description, userId } = await request.json();

  // Step 1：图片 hash
  const hash = await sha256(imageUrl);

  // Step 2：检查缓存
  const cached = await env.DB.prepare(
    "SELECT result FROM diagnose_cache WHERE image_hash = ?"
  ).bind(hash).first();
  if (cached) return Response.json(cached.result);

  // Step 3：限流检查
  const rateLimited = await checkRateLimit(userId, env);
  if (rateLimited) return new Response("Rate limited", { status: 429 });

  // Step 4：预算检查
  const budgetOk = await checkBudget(env);
  const provider = budgetOk ? "zhipu" : "qwen";  // 自动降级

  // Step 5：调 LLM
  const result = await callLLM(provider, { imageUrl, waterFreq, light, soil, description });

  // Step 6：缓存写入
  await env.DB.prepare(
    "INSERT INTO diagnose_cache (image_hash, result, created_at) VALUES (?, ?, ?)"
  ).bind(hash, JSON.stringify(result), Date.now()).run();

  // Step 7：log
  await env.DB.prepare(
    "INSERT INTO api_logs (user_id, provider, cost, latency) VALUES (?, ?, ?, ?)"
  ).bind(userId, provider, estimateCost(provider), Date.now() - start).run();

  return Response.json(result);
}
```
