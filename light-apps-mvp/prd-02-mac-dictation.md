## 0. 一句话定位

一个**常驻菜单栏、按住快捷键说话就把文字打进任意 App** 的听写工具，**全程在本机跑**（端侧 Whisper / Parakeet / Apple 语音），主打 **"中英混说 + 技术词汇 + 真私有 + 一次买断"**，对标月费 $15 且**每句话都上传服务器**的云端老大 Wispr Flow。

> 运行时端侧零云、零边际成本：模型首次下载后永久离线，毛利 ≈ 100%，与"一次性买断"的商业数学自洽。

## 1. 背景与痛点

### 1.1 市场在快速变大（证据强度：强）

- **语音输入正在从"医生/律师的小众技巧"变成知识工作者愿意付费的主流交互层。** 语音 AI 市场 2026 年约 **$22.5B、34–35% CAGR**，2031 预计约 **$61.7B**（多份市场报告交叉，中-高）。
- **类目老大 Wispr Flow 被资本疯狂加注**：2026-05 Bloomberg 报道其以**接近 $20 亿估值**、Menlo 领投融 ~$2.6 亿，半年估值近乎翻 3 倍；**累计 ~250 万次下载**、服务 **270 家世界 500 强**（含 Nvidia、Amazon）；GetLatka 记录其 ~$10M ARR（强：Bloomberg / PitchBook / Tracxn 多源）。

### 1.2 老大的软肋极其明确 = 我们的进攻面（证据强度：强）

1. **纯订阅** $15/mo 或 $144/yr，**没有任何买断/终身选项**（截至 2026-04 仍如此）；
2. **每一句话都上传到它的服务器处理**——医疗 / 法务 / 企业合规 / 隐私敏感人群**不能用**。

这两点正是"**本地 + 买断**"的完美进攻楔子：不是和免费开源拼刺刀，而是对一大批人（隐私党、合规行业、反订阅党）提供**结构性更优解**。

### 1.3 开发者对通用听写的一手抱怨（证据强度：中-强）

- "GraphQL 被打成 **graph cool**"；
- Apple 自带听写"**糟蹋技术术语、一半时间无视标点、偶尔直接罢工**"；
- **无法添加自定义词汇 / 缩写 / 领域术语**；
- 技术内容准确率仅 **60–70%**，要大量手改。

### 1.4 被严重忽视的刚需：中英混说（code-switching）

> "我说一句中文里夹 Kubernetes、PR、merge 一下" —— 这是中文开发者**每天真实的说话方式**，而主流听写工具几乎都是**英文优先**，对混说处理得很差。**这是我们作为中文工程师的"不公平优势"切口。**

## 3. 功能列表

### 3.1 MVP（P0，1 周目标）

| 模块 | 能力 |
|---|---|
| 菜单栏常驻 | `MenuBarExtra` 图标 + 状态（空闲 / 录音中 / 转写中），开始/停止、设置、退出 |
| 全局热键 | 按住自定义热键（默认 `fn`，或 `⌥Space`）→ 录音；松开 → 停止并转写 |
| 端侧录音 | `AVAudioEngine` 采集麦克风，16kHz 单声道 PCM 缓冲（Whisper 输入格式） |
| 端侧转写 | 本机模型转写（MVP：1 个本地模型 + 中英双语 / 中英混说） |
| 文本注入 | 转写结果通过 `CGEvent` 模拟键盘**打进当前焦点 App 光标处** |
| 自定义词典 | 一个本地词典文件（技术词 / 缩写 / 项目术语），转写后做替换纠正 |
| 设置面板 | 模型选择、语言（中 / 英 / **中英混**）、热键自定义 |

### 3.2 P1（验证有人尖叫后做）

- AI 后处理：口语 → 规范文本、自动加标点、"整理成结构化 prompt"（用 **Apple Foundation Models 端侧**，零云）；
- 口述代码符号：camelCase / snake_case / 括号 / 管道符的语音指令；
- 分应用模式（不同 App 用不同词典 / 语言）；
- 多模型管理 + 模型下载中心。

### 3.3 明确不做（MVP）

- ❌ 任何云转写 / 云后处理（这是产品的反卖点，永不做"默认上云"）；
- ❌ 付费墙（MVP 先免费发 HN / r/macapps 验证"中英混说 + 离线"是否有人尖叫）；
- ❌ Windows / 跨平台。

## 5. 差异化楔子（聚焦三选一，MVP 押第 1 个）

1. **【主押】中英 / 多语混说第一好用** —— 中文开发者市场，海外英文工具普遍不重视。这是中文工程师的不公平优势切口。

> MVP 阶段：**主押 1（中英混说）**，附带 3 的"零网络可验证"作为信任背书。2 留到 P1。

## 7. 技术选型

### 7.1 为什么必须 Swift/SwiftUI，不能用 Tauri/Electron（证据强度：强）

| 关键能力 | 依赖的系统 API | Tauri/Electron 行不行 |
|---|---|---|
| 全局热键（按住说话） | Carbon `RegisterEventHotKey` / `CGEventTap` | ❌ 别扭、体验差 |
| 把文字注入任意 App | `CGEvent` 键盘事件 / Accessibility | ❌ 调不到 / 不稳 |
| 菜单栏常驻 | `MenuBarExtra`（SwiftUI）/ `NSStatusItem` | ⚠️ 有团队反馈 **Tauri 菜单控制弱、感觉过时**，最终转回 Swift |
| 端侧转写 | **WhisperKit（Swift / CoreML / Metal）** 原生最顺 | ❌ 绕一层桥接，性能/工程都差 |
| 端侧后处理（P1） | **Apple Foundation Models**（仅 Swift 可调） | ❌ 只能 Swift |

**结论**：本产品的**每一个核心能力**都命中"只能/最好用 Swift"的系统底层。Tauri 体积虽是 Electron 的 1/10\~1/100，但仍大于无 Chromium 的原生 Swift，且菜单栏体验打折。**Swift/SwiftUI（+ 少量 AppKit）是唯一正确选择。**

社区经验：菜单栏 App ≈ **70% SwiftUI（视图/状态）+ 30% AppKit（系统集成）**；真正的难点不在语言，而在"**系统权限 + 跨 App 兼容性**"（即文本注入 + 全局热键）。

### 7.2 端侧转写引擎：WhisperKit vs Apple SFSpeechRecognizer 的权衡

| 维度 | **WhisperKit**（推荐 P0+） | **Apple SFSpeechRecognizer + on-device** | whisper.cpp / Parakeet-MLX |
|---|---|---|---|
| 中英混说 | ✅ **multilingual 模型原生支持 code-switching**（核心卖点靠它） | ⚠️ 单语 locale 为主，混说弱 | ✅（whisper 系同源） |
| 技术词准确率 | ✅ 可结合自定义词典 / prompt | ❌ 受限，且无法注入词典 | ✅ |
| 真离线 / 零云 | ✅ 模型首次下载后**永久离线** | ⚠️ `requiresOnDeviceRecognition=true` 才离线，部分 locale 仍可能回落云端 | ✅ 完全离线 |
| 模型体积 / 下载 | ⚠️ 需下载模型（tiny\~large，几十 MB\~GB），首次有带宽成本 | ✅ 系统自带，零下载 | ⚠️ 需下载 |
| 集成成本 | 中（SPM 依赖 + 模型管理） | **低**（系统 API） | 高（C++ / 桥接 / 手写 Metal） |
| 许可 | MIT（WhisperKit 本体） | 系统 | whisper.cpp MIT；Parakeet 看许可 |

**选型决策**：

- **P0 主引擎 = WhisperKit**：因为"中英混说 + 技术词 + 真离线可验证"这三个核心卖点**只有 multilingual Whisper 系能同时满足**，Apple SFSpeechRecognizer 在混说和词典注入上结构性受限。
- **保底 / 快速验证路径 = Apple SFSpeechRecognizer（on-device）**：作为"零下载、开箱即用"的降级选项，让没下模型的用户也能先体验（设置里可切换）。
- **抽象层设计**：定义 `TranscriptionEngine` protocol，把引擎差异隔离在一层之下，MVP 先用 `MockEngine` 跑通全链路，再接 `WhisperKitEngine`。这样引擎可替换、可并存、可灰度。

> 关于"运行时零云成本"：WhisperKit/Parakeet 全本地 GPU(Metal) 跑，VoiceInk/superwhisper/Plae 已证明工程可行。**运行时云 LLM 成本 = 0**，唯一边际成本是首次模型下载带宽（一次性、走 Apple/HF CDN）。

### 7.3 关键技术风险点（开发最深的坑）

1. **文本注入的跨 App 兼容性**：`CGEvent` 在不同 App（Electron 应用、终端、密码框）行为不一，需逐一验证 + 提供"复制到剪贴板再粘贴"的兜底策略。
2. **全局热键 + 权限**：`CGEventTap` 监听需要"辅助功能"授权；按住/松开语义需要可靠的 keyDown/keyUp 配对。
3. **音频采集**：`AVAudioEngine` 的采样率转换（设备原生 → 16kHz），低延迟 buffer。
4. **MAS 沙盒**：文本注入 + 全局热键在沙盒下受限，故主分发走官网（见 6.2）。

## 8. 一周 MVP 范围（DoD）

**目标链路**：按住 `fn`（或自定义热键）→ 录音 → 端侧转写 → 文本自动注入当前光标处。

| Day | 交付 |
|---|---|
| 1 | 工程骨架：`MenuBarExtra` app + 菜单 UI + 设置面板 + 状态机 |
| 2 | `AVAudioEngine` 录音 + 全局热键（Carbon `RegisterEventHotKey`）按住/松开 |
| 3 | `TranscriptionEngine` 抽象 + `MockEngine` 跑通全链路（不依赖真实模型） |
| 4 | `CGEvent` 文本注入 + 剪贴板兜底；自定义词典替换 |
| 5 | 接 `WhisperKitEngine`（SPM + 模型下载），中英混说实测 |
| 6 | 打磨：权限引导、错误处理、设置持久化（`UserDefaults`） |
| 7 | 真机验证 + README + 发 HN / r/macapps（免费版） |

**MVP 只支持**：1 个本地模型 + 中英双语/混说 + 一个自定义词典文件。**先不做** AI 后处理、多模型管理、付费墙。

**验收标准（DoD）**：
1. 在 Notes / Cursor / 浏览器输入框，按住热键说一句"帮我 merge 一下这个 PR"，文字正确出现在光标处；
2. 断开网络后仍能完成转写（证明真离线）；
3. 词典能把"graph cool"纠正成"GraphQL"。

## 9. 风险评估（诚实）

| 风险 | 等级 | 说明 / 缓解 |
|---|---|---|
| **已有强竞品占坑** | ⚠️ 中-高 | VoiceInk（开源 $25）几乎是"理想答案"。**缓解：绝不做通用听写，死磕"中英混说"单一楔子**，做到"中文开发者用过就回不去"。 |
| 开发最重 | ⚠️ 中 | 系统注入 + 音频 + 端侧模型，三个方案里最重。1 周只能跑通核心，打磨到丝滑要更久。**缓解：可参照 VoiceInk 开源架构（GPLv3，注意传染，不拷代码进闭源）。** |
| 文本注入兼容性 | ⚠️ 中 | 各 App 行为不一。**缓解：CGEvent + 剪贴板粘贴双策略 + 兼容性清单。** |
| "本地/离线"已非护城河 | ⚠️ 中 | 听写早有免费离线版。真护城河 = **细分人群（中文混说）+ 体验质量**，不是"又一个离线工具"。 |
| Apple 端侧能力变强 | ⚠️ 低-中 | 系统听写持续进步有"被吃掉"风险。**缓解：靠 multilingual + 自定义词典 + 隐私可验证做差异，这些系统短期补不齐。** |
| 模型下载体验 | ⚠️ 低 | 首次几十 MB\~GB 下载。**缓解：默认推 small 模型 + 进度 UI + Apple SFSpeech 作为"零下载"降级。** |

**一句话总结风险**：市场和痛点都被资本+用户双重验证过，但**这是红海里的一条窄缝**——成败完全取决于"中英混说"这个楔子能不能做到让中文开发者尖叫。技术不是最大风险，**聚焦和打磨才是**。
